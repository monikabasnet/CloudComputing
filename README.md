# CA0 – Manual Cloud Deployment

## Purpose

CA0 established the manually deployed reference architecture for the authentication-threat monitoring system.

A distributed pipeline was deployed on AWS using four EC2 virtual machines.

The application flow is:

```text
Authentication Event Producer
            |
            v
      Apache Kafka
       auth-events
            |
            v
     Threat Processor
            |
            v
         MongoDB
            |
            v
        REST API
```

Synthetic authentication events are generated by the Producer and published to Kafka.

The Processor consumes the events, tracks repeated failed authentication attempts, assigns a classification, persists the processed events in MongoDB, and exposes the stored information through a REST API.

---

## CA0 Architecture

Four EC2 instances are used:

| Component | Responsibility |
|---|---|
| Producer | Generates synthetic authentication events |
| Kafka Broker | Provides Pub/Sub event streaming |
| Processor | Consumes and classifies authentication events |
| MongoDB | Persists processed security events |

Private IPv4 communication is used between application components.

The Processor also exposes the REST API on port `8080`.

| Layer | Technology |
|---|---|
| Cloud Provider | AWS |

| Operating System | Ubuntu Server 24.04 LTS |

Kafka is deployed as a single-node KRaft broker.

MongoDB is deployed as a standalone database.

The Producer and Processor applications are containerized.

---

## CA0 Threat Detection

Authentication events are classified using consecutive failed login attempts for the same:

```text
username + source_ip
```

The classification logic is:

| Failed Attempts | Classification |
|---:|---|
| Successful login | `NORMAL` |
| 1–2 | `FAILED_LOGIN` |
| 3–4 | `SUSPICIOUS` |
| 5+ | `POSSIBLE_BRUTE_FORCE` |

A successful authentication resets the active failure counter.

The detection rule is an educational stream-processing heuristic and is not intended to represent a production intrusion-detection system.

## CA0 Pipeline Validation

The CA0 deployment demonstrated the complete path:

```text
Producer
   |
   v
Kafka
   |
   v
Processor
   |
   v
MongoDB
```

Processed information could then be retrieved through:

```text
MongoDB
   |
   v
Processor REST API
   |
   v
Client
```

The following REST endpoints were implemented:

```text
GET /health
GET /events
GET /alerts
```

Repeated failed authentication events were also generated until the following progression was observed:

```text
FAILED_LOGIN
FAILED_LOGIN
SUSPICIOUS
SUSPICIOUS
POSSIBLE_BRUTE_FORCE
```

The resulting `POSSIBLE_BRUTE_FORCE` event was persisted in MongoDB and returned through the `/alerts` endpoint.

## CA0 Security

Security measures implemented during CA0 include:

- SSH key-based administration
- AWS Security Groups
- private service-to-service communication
- MongoDB authentication
- restricted MongoDB application account
- protected runtime credential file
- non-root Producer container
- non-root Processor container
- credentials excluded from application source code
- MongoDB bound to required interfaces instead of `0.0.0.0`

The Processor MongoDB account was granted application-level access rather than administrative database privileges.

---

## CA0 Design Trade-offs

The CA0 architecture intentionally favored direct administration and visibility into each component.

Four EC2 instances were used to separate the Producer, Kafka Broker, Processor, and MongoDB database.

A single Kafka broker and standalone MongoDB instance reduced resource usage but did not provide production high availability.

The REST API was hosted inside the Processor rather than on an additional VM.

The Producer was executed on demand because it acts as a synthetic event generator rather than a continuously running production service.

CA0 therefore prioritized manual deployment experience and understanding of the individual distributed-system components.

# CA1 – Infrastructure as Code

## Purpose

CA1 converts the manually deployed CA0 reference environment into an automated **Infrastructure as Code** implementation.

The functional application architecture is retained, while infrastructure provisioning, host configuration, deployment, validation, and teardown are automated.

The CA1 pipeline remains:

```text
Producer
   |
   v
Kafka
   |
   v
Processor
   |
   v
MongoDB
   |
   v
REST API
```

The major change is the deployment model:

```text
CA0
Manual AWS + Service Configuration
             |
             v
CA1
Terraform + Ansible + Automation Scripts
```

---

## CA1 Infrastructure Automation

**Terraform** is used to provision:

- AWS VPC
- subnet
- routing
- Internet gateway
- security groups
- security-group rules
- SSH key resource
- four EC2 instances

**Ansible** is used to configure:

- common operating-system packages
- Docker
- MongoDB
- Kafka
- Processor
- Producer

Bash scripts coordinate the complete lifecycle.

---

## CA1 Reproducibility

The complete infrastructure lifecycle was tested:

```text
Deploy
  |
  v
Validate
  |
  v
Destroy
  |
  v
Redeploy
  |
  v
Validate Again
```

The Terraform-managed environment was completely removed and subsequently recreated from the project automation.

The recreated environment received new AWS resource identifiers and network addresses.

The Ansible inventory was regenerated from the new Terraform outputs, services were configured, and the pipeline was successfully validated again.

This demonstrated that the CA1 deployment does not depend on retaining the original EC2 instances.

---

## CA1 Security

Security controls include:

- dedicated non-root AWS IAM identity for Terraform
- Ansible Vault for MongoDB credentials
- Terraform state excluded from Git
- local Terraform variables excluded from Git
- private SSH keys excluded from Git
- Vault password excluded from Git
- SSH administration restricted by `/32` CIDR
- Kafka access restricted through security groups
- MongoDB application access restricted to the Processor
- credentials excluded from Terraform outputs

# CA0 to CA1 Progression

The assignments demonstrate a transition from manual cloud administration to reproducible cloud automation.

| Area | CA0 | CA1 |
|---|---|---|
| Infrastructure | Manually created | Terraform-managed |
| EC2 Instances | Manual | Terraform |
| Networking | Manual | Terraform |
| Security Groups | Manual | Terraform |
| Host Configuration | Manual | Ansible |
| Kafka Deployment | Manual | Ansible |
| MongoDB Deployment | Manual | Ansible |
| Processor Deployment | Manual Docker workflow | Ansible-managed Docker |
| Producer Deployment | Manual Docker workflow | Ansible-managed Docker |
| Inventory | Manually known hosts | Generated from Terraform |
| Secrets | Protected runtime configuration | Ansible Vault |
| Validation | Manual commands | Automated validation script |
| Teardown | Manual | Automated Terraform destroy |
| Reproduction | Documented manual process | Automated lifecycle |

The application purpose remains consistent between assignments while the deployment methodology becomes progressively more automated and reproducible.
