\# CA0: Authentication Threat Monitoring Pipeline

## Overview

A distributed authentication threat monitoring pipeline was manually deployed on Amazon Web Services (AWS) for CA0.

Synthetic authentication events are generated by a containerized Producer and published to Apache Kafka. The events are consumed by a containerized Processor, where repeated failed authentication attempts are classified. Processed events are stored in MongoDB and can be retrieved through a REST API.

The primary data pipeline is:

```text
Producer -> Kafka -> Processor -> MongoDB
```

Processed information can also be retrieved through:

```text
MongoDB -> Processor REST API -> Client
```

Four EC2 virtual machines were used so that the Producer, Kafka Broker, Processor, and MongoDB database could be separated.

AWS Free Tier resources were used for the deployment. Available Free Tier resources and cloud cost were considered when the architecture was selected.

The cybersecurity use case is based on repeated failed authentication attempts. Authentication events are classified as:

```text
NORMAL
FAILED_LOGIN
SUSPICIOUS
POSSIBLE_BRUTE_FORCE
```

The detection rule was created as an educational example of stream processing and is not intended to represent a production intrusion detection system.

# Technology Choices and Tradeoffs

The technology stack was selected based on the assignment requirements, available resources, cost, deployment complexity, and the need to understand each pipeline component manually.

The selected stack consists of:

```text
AWS EC2
Ubuntu
Docker
Apache Kafka
Python
MongoDB
Flask
Git and GitHub
```

Each technology provided advantages, but tradeoffs were also considered.

## Amazon Web Services

Amazon Web Services was selected because AWS Free Tier resources were available for the project.

The required virtual machines and networking environment could therefore be created while cloud cost was minimized.

Four EC2 instances were used:

```text
Producer
Kafka Broker
Processor
MongoDB Database
```

Separate EC2 instances allowed communication between distributed services to be configured and tested manually.

### Advantages

- AWS Free Tier resources were available.
- Direct access to Ubuntu virtual machines was provided through EC2.
- Private networking could be used between services.
- Security Groups could be used to restrict inbound communication.
- Individual application responsibilities could be separated between hosts.
- The manual EC2 environment matched the purpose of CA0.

### Tradeoffs

More administration was required than would have been required with managed cloud services.

The following tasks had to be performed manually:

```text
Operating system configuration
Package installation
Kafka configuration
MongoDB configuration
Docker installation
Network configuration
Service startup
Authentication
Logging
Troubleshooting
```

This additional work was accepted because manual deployment and understanding the individual components were primary goals of CA0.

AWS Free Tier availability also influenced the architecture. Additional virtual machines were avoided when they were unnecessary.

For example, a separate REST API VM was not created. The REST API was hosted by the existing Processor container.

---

## Apache Kafka

Apache Kafka 4.3.1 was selected as the Pub/Sub system.

Kafka separates event production from event processing:

```text
Producer
    |
    v
Kafka
    |
    v
Processor
```

### Advantages

- Asynchronous messaging is supported.
- Producers and consumers are decoupled.
- Consumer offsets can be tracked.
- Events can be retained by the Broker.
- Kafka is widely used for event-streaming systems.
- The technology directly matched the Pub/Sub requirement.

### Tradeoffs

More configuration was required than would have been required with direct communication between the Producer and Processor.

Java, KRaft storage, listeners, topics, and service configuration had to be managed.

A single Kafka Broker was used because the assignment environment was limited to four VMs.

The topic therefore uses:

```text
Partitions: 1
Replication Factor: 1
```

This configuration is appropriate for the assignment but does not provide production fault tolerance.

---

## Kafka KRaft

Kafka was configured using KRaft mode instead of ZooKeeper.

Kafka 4.3.1 supports metadata management through KRaft, so a separate ZooKeeper service was not required.

### Advantage

One additional infrastructure service did not need to be deployed or maintained.

### Tradeoff

Kafka storage initialization and controller configuration still had to be completed manually.

---

## MongoDB

MongoDB 8.0.29 was selected for persistent storage.

Processed authentication events are naturally represented as document records.

Example:

```json
{
  "event_id": "example-id",
  "username": "alice",
  "source_ip": "192.0.2.15",
  "success": false,
  "failed_attempts": 5,
  "status": "POSSIBLE_BRUTE_FORCE"
}
```

### Advantages

- JSON-like event structures can be stored naturally.
- PyMongo provides direct Python integration.
- Flexible document structures are supported.
- Processed security events can be queried easily.

### Tradeoffs

A single MongoDB instance was used.

No replica set or database high availability was configured.

An unexpected Linux kernel compatibility problem was also encountered and had to be resolved manually.

---

## Docker

Docker was selected for the Producer and Processor.

### Advantages

- Application dependencies are isolated.
- Reproducible application images can be built.
- Python versions and dependencies can be controlled.
- Non-root users can be configured.
- Deployment commands remain consistent.

### Tradeoffs

Container lifecycle, image versions, environment variables, logs, and restart policies had to be managed in addition to the EC2 hosts.

---

## Python

Python 3.12 was used for the Producer and Processor.

### Advantages

- Kafka and MongoDB client libraries are available.
- JSON event processing is straightforward.
- The application code remains relatively small.
- Flask can be integrated into the Processor.

### Tradeoff

The current threat Processor keeps consecutive failure counters in application memory.

A more advanced distributed implementation would require durable state management.

---

## Flask

Flask 3.1.2 was selected for the REST API.

### Advantages

- Minimal API code was required.
- Flask could be integrated directly into the existing Processor.
- An additional VM was not required.
- MongoDB data could be returned through HTTP endpoints.

### Tradeoffs

The Flask development server is currently used.

This is suitable for the assignment demonstration but would not be appropriate for a production deployment.

A production system would normally use a production WSGI server, TLS, and API authentication.

# Producer

A Python Producer was created to generate synthetic authentication events.

An example event is:

```json
{
  "event_id": "16fdbfb3-3813-4e25-9351-f6a30f0a8fe0",
  "username": "alice",
  "source_ip": "192.0.2.15",
  "success": false,
  "timestamp": "2026-09-06T10:13:30.990067+00:00"

```

A UUID is generated for each event.

The UUID allows the same event to be traced through the pipeline:

```text

   |

Processor
   |
   | same event_id

MongoDB
```

# Threat Processor

A Python Processor was created to consume authentication events from Kafka.

The processing sequence is:

```text
Kafka Event
     |
     v
JSON Deserialization
     |
     v
Failed Login Tracking
     |
     v
Threat Classification
     |
     v
MongoDB Insert
     |
     v
Kafka Offset Commit
```

---

## Threat Classification

Consecutive failed authentication attempts are tracked using:

```text
(username, source_ip)
```

The following rule was implemented:

| Failed Attempts | Classification |
|---:|---|
| Successful login | `NORMAL` |
| 1 | `FAILED_LOGIN` |
| 2 | `FAILED_LOGIN` |
| 3 | `SUSPICIOUS` |
| 4 | `SUSPICIOUS` |
| 5 or more | `POSSIBLE_BRUTE_FORCE` |

A successful login resets the counter.

The threshold is used only as an educational heuristic.

Five failed logins are not claimed to prove that a real brute-force attack has occurred.

---

# Kafka Offset Handling

The original Processor used:

```python
enable_auto_commit=True
```

During testing, MongoDB authentication failed after Kafka messages had already been consumed.

The Kafka consumer group was inspected and offsets were found to have advanced despite failed database writes.

The implementation was changed to:

```python
enable_auto_commit=False
```

The MongoDB insertion is performed first:

```python
result = collection.insert_one(processed_event)
```

The Kafka offset is then committed:

```python
consumer.commit()
```

The final sequence is:

```text
Kafka Event
    |
    v
Processor
    |
    v
MongoDB Write
    |
    | successful
    v
Kafka Commit
```

Exactly-once processing is not claimed.

# Problems Encountered and Changes Made

Several problems were encountered during deployment.

The failures were documented because they affected the final implementation.

## Kafka KRaft Initialization

The initial Kafka storage formatting command failed because an explicit controller initialization option was required.

A single-node Kafka deployment was being used, so:

```text
--standalone
```

was selected.

Kafka was then initialized successfully.

---

## MongoDB Kernel Compatibility

MongoDB 8.0.29 was installed successfully, but the service initially failed to start.

The problem was investigated using:

```bash
sudo systemctl status mongod
sudo journalctl -u mongod -n 30 --no-pager
```

A compatibility issue with the running Linux kernel was reported.

The Database VM was running:

```text
7.0.0-1012-aws
```

A compatible installed kernel was identified:

```text
6.17.0-1017-aws
```

The GRUB configuration was backed up and configured to use the compatible kernel.

After reboot:

```bash
uname -r
```

returned:

```text
6.17.0-1017-aws
```

MongoDB then started successfully.

---

## MongoDB User Configuration

A placeholder password was accidentally used during the first creation of the MongoDB Processor user.

The existing account was corrected using:

```text
db.updateUser(...)
```

Authentication was then validated independently.

---

## Processor Authentication Failure

During the first Processor test, Kafka events were received successfully but MongoDB returned:

```text
Authentication failed
```

The MongoDB application account was tested directly.

The account was valid.

The Processor runtime configuration was then corrected.

MongoDB insertion succeeded afterward.

---

## Kafka Offset Handling

Automatic Kafka offset commits were used in the first Processor implementation.

Offsets were observed advancing even when MongoDB writes had failed.

Automatic commits were disabled.

Manual commits were added after successful MongoDB insertion.

---

## Processor Container Lifecycle

The Processor was initially executed using:

```text
docker run --rm
```

during interactive testing.

The final deployment was changed to:

```text
docker run -d
```

with:

```text
--restart unless-stopped
```

so that the Processor could remain running independently of the SSH session.

# Deviations from the Reference Stack

## KRaft Instead of ZooKeeper

Kafka was deployed using KRaft instead of ZooKeeper.

KRaft provides the metadata quorum functionality required by the selected Kafka version.

## Single Kafka Broker

A single Kafka Broker was deployed because the assignment environment was limited to four VMs and AWS Free Tier resources were being used.

Replication factor 1 was therefore used.

## Single MongoDB Instance

MongoDB was deployed as a standalone database rather than a replica set.

This reduced resource usage but does not provide database high availability.

## REST API Inside Processor

A separate API VM was not created.

The Flask REST API was hosted inside the Processor container to avoid an unnecessary additional EC2 instance.

## Producer Executed on Demand

The Producer is a synthetic event simulator.

It is executed when controlled test events need to be generated rather than being operated as a continuously running service.

The `auth-events` topic should be created.

Kafka should be enabled through systemd.

MongoDB should be installed on the Database VM.

MongoDB should be bound to localhost and the private database interface.

Authorization should be enabled.

A restricted Processor user should be created.

  -t ca0-auth-producer:1.0 .
