# CA0 – Authentication Threat Monitoring Pipeline

## Overview

A distributed authentication-threat monitoring pipeline was manually deployed on Amazon Web Services (AWS) for CA0.

Synthetic authentication events are generated by a containerized Producer and published to Apache Kafka. The events are consumed by a containerized Processor, where repeated failed authentication attempts are classified. Processed events are stored in MongoDB and can be retrieved through a REST API.

The primary data pipeline is:

```text
Producer -> Kafka -> Processor -> MongoDB
```

Processed information can also be retrieved through:

```text
MongoDB -> Processor REST API -> Client
```

Four EC2 virtual machines were used so that the Producer, Kafka Broker, Processor, and MongoDB database could be separated.

The cybersecurity use case is based on repeated failed authentication attempts. Authentication events are classified as:

```text
NORMAL
FAILED_LOGIN
SUSPICIOUS
POSSIBLE_BRUTE_FORCE
```

The detection rule was created as an educational example of stream processing and is not intended to represent a production intrusion-detection system.

# Technology Choices and Trade-offs

The technology stack was selected based on the assignment requirements, available cloud resources, deployment complexity, and the need to understand each pipeline component manually.

The selected stack consists of:

```text
AWS EC2
Ubuntu
Docker
Apache Kafka
Python
MongoDB
Flask
Git and GitHub
```

## Amazon Web Services

AWS was selected as the cloud platform.

Four EC2 instances were used:

```text
Producer
Kafka Broker
Processor
MongoDB Database
```

Separate EC2 instances allowed communication between distributed services to be configured and tested manually.

### Advantages

- Direct access to Ubuntu virtual machines was provided through EC2.
- Private networking could be used between services.
- Security Groups could restrict inbound communication.
- Individual application responsibilities could be separated between hosts.
- The environment provided direct experience administering cloud infrastructure.

### Trade-offs

More administration was required than would have been required with managed cloud services.

The following tasks were performed manually:

```text
Operating-system configuration
Package installation
Kafka configuration
MongoDB configuration
Docker installation
Network configuration
Service startup
Authentication
Logging
Troubleshooting
```

This additional work was accepted because manual deployment and understanding the individual components were primary goals of CA0.

A separate REST API VM was not created. The REST API was hosted by the existing Processor container.

---

## Apache Kafka

Apache Kafka 4.3.1 was selected as the Pub/Sub system.

Kafka separates event production from event processing:

```text
Producer
   |
   v
Kafka
   |
   v
Processor
```

### Advantages

- asynchronous messaging is supported;
- Producers and Consumers are decoupled;
- Consumer offsets can be tracked;
- events can be retained by the Broker;
- Kafka is widely used for event-streaming systems;
- the technology directly matched the Pub/Sub requirement.

### Trade-offs

Kafka required additional configuration compared with direct Producer-to-Processor communication.

Java, KRaft storage, listeners, topics, and service configuration had to be managed.

A single Kafka Broker was used.

The topic therefore uses:

```text
Partitions: 1
Replication Factor: 1
```

This configuration is suitable for the assignment but does not provide production fault tolerance.

---

## Kafka KRaft

Kafka was configured using KRaft mode instead of ZooKeeper.

Kafka 4.3.1 supports metadata management through KRaft, so a separate ZooKeeper service was not required.

### Advantage

An additional infrastructure service did not need to be deployed or maintained.

### Trade-off

Kafka storage initialization and controller configuration still required explicit configuration during the manual CA0 deployment.

---

## MongoDB

MongoDB 8.0.29 was selected for persistent storage.

Processed authentication events are naturally represented as document records.

Example:

```json
{
  "event_id": "example-id",
  "username": "alice",
  "source_ip": "192.0.2.15",
  "success": false,
  "failed_attempts": 5,
  "status": "POSSIBLE_BRUTE_FORCE"
}
```

### Advantages

- JSON-like event structures can be stored naturally.
- PyMongo provides direct Python integration.
- Flexible document structures are supported.
- Processed security events can be queried easily.

### Trade-offs

A single MongoDB instance was used.

No replica set or database high availability was configured.

A Linux kernel compatibility problem was also encountered during CA0 and had to be resolved manually.

---

## Docker

Docker was selected for the Producer and Processor.

### Advantages

- application dependencies are isolated;
- reproducible application images can be built;
- Python versions and dependencies can be controlled;
- non-root users can be configured;
- deployment commands remain consistent.

### Trade-offs

Container lifecycle, image versions, environment variables, logs, and restart policies had to be managed in addition to the EC2 hosts.

---

## Python

Python 3.12 was used for the Producer and Processor.

### Advantages

- Kafka and MongoDB client libraries are available.
- JSON event processing is straightforward.
- The application code remains relatively small.
- Flask can be integrated into the Processor.

### Trade-off

The threat Processor keeps consecutive failure counters in application memory.

A more advanced distributed implementation would require durable state management.

---

## Flask

Flask 3.1.2 was selected for the REST API.

### Advantages

- minimal API code was required;
- Flask could be integrated directly into the Processor;
- an additional VM was not required;
- MongoDB data could be returned through HTTP endpoints.

### Trade-offs

The Flask development server is used.

This is suitable for the assignment demonstration but is not intended as a production deployment.

A production system would normally use a production WSGI server, TLS, and API authentication.

# Threat Processor

A Python Processor consumes authentication events from Kafka.

The processing sequence is:

```text
Kafka Event
     |
     v
JSON Deserialization
     |
     v
Failed Login Tracking
     |
     v
Threat Classification
     |
     v
MongoDB Insert
     |
     v
Kafka Offset Commit
```

---

## Threat Classification

Consecutive failed authentication attempts are tracked using:

```text
(username, source_ip)
```

The implemented classification is:

| Failed Attempts | Classification |
|---:|---|
| Successful login | `NORMAL` |
| 1 | `FAILED_LOGIN` |
| 2 | `FAILED_LOGIN` |
| 3 | `SUSPICIOUS` |
| 4 | `SUSPICIOUS` |
| 5 or more | `POSSIBLE_BRUTE_FORCE` |

A successful login resets the active counter.

The threshold is an educational heuristic. Five failed logins are not claimed to prove that a real brute-force attack has occurred.

---

## Processed Event

The Processor adds classification information.

Example:

```json
{
  "event_id": "15b29141-7760-4c47-bbba-bca10ba673b2",
  "username": "alice",
  "source_ip": "192.0.2.15",
  "success": false,
  "timestamp": "2026-09-06T10:44:35.551109+00:00",
  "failed_attempts": 5,
  "status": "POSSIBLE_BRUTE_FORCE"
}
```

The processed document is stored in:

```text
threat_monitor.security_events
```

# Kafka Offset Handling

The original Processor used:

```python
enable_auto_commit=True
```

During testing, MongoDB authentication failed after Kafka messages had already been consumed.

The Kafka consumer group was inspected and offsets were found to have advanced despite failed database writes.

The implementation was changed to:

```python
enable_auto_commit=False
```

MongoDB insertion is performed first.

The Kafka offset is committed only after the database write succeeds.

The final sequence is:

```text
Kafka Event
    |
    v
Processor
    |
    v
MongoDB Write
    |
    | successful
    v
Kafka Commit
```

Exactly-once processing is not claimed.

# Problems Encountered and Changes Made

Several problems were encountered during the manual deployment.

The failures were documented because they affected the final implementation.

## Kafka KRaft Initialization

Initial Kafka storage formatting required configuration appropriate for the single-node KRaft deployment.

Kafka was then initialized successfully.

---

## MongoDB Kernel Compatibility

MongoDB 8.0.29 was installed successfully, but the service initially failed to start.

The problem was investigated through service status and journal logs.

A compatible installed kernel was selected and the Database VM was rebooted.

MongoDB then started successfully.

---

## MongoDB User Configuration

A placeholder password was accidentally used during the first creation of the MongoDB Processor user.

The account was corrected and authentication was subsequently validated independently.

This incident was retained in the documentation because it was part of the implementation and verification process.

---

## Processor Authentication Failure

During the first Processor test, Kafka events were received successfully but MongoDB returned:

```text
Authentication failed
```

The MongoDB application account was tested directly.

The account was valid.

The Processor runtime configuration was then corrected and MongoDB insertion succeeded.

---

## Kafka Offset Handling

Automatic Kafka offset commits were used in the first Processor implementation.

Offsets were observed advancing even when MongoDB writes failed.

Automatic commits were disabled and manual commits were added after successful MongoDB insertion.

---

## Processor Container Lifecycle

The Processor was initially executed interactively during testing.

The final deployment was changed to a detached container using:

```text
--restart unless-stopped
```

so that it could remain operational independently of the SSH session.

# Deviations and Design Decisions

## KRaft Instead of ZooKeeper

Kafka was deployed using KRaft rather than ZooKeeper.

A separate ZooKeeper service was therefore not required.

## Single Kafka Broker

A single Kafka Broker was deployed.

Replication factor `1` was therefore used.

This reduces resource usage but does not provide Kafka high availability.

## Single MongoDB Instance

MongoDB was deployed as a standalone database rather than a replica set.

This reduces resource requirements but does not provide database high availability.

## REST API Inside Processor

A separate API VM was not created.

The Flask REST API was hosted inside the Processor container.

## Producer Executed on Demand

The Producer is a synthetic event simulator.

It is executed when controlled test events need to be generated rather than operating as a continuously running service.
