# Claim

A distributed authentication threat monitoring pipeline was manually deployed and validated on Amazon Web Services.

The following pipeline was demonstrated:

```text
Producer
   |
   v
Kafka
   |
   v
Threat Processor
   |
   v
MongoDB
   |
   v
REST API
```

Four EC2 instances were used.

The responsibilities were separated as:

```text
Producer VM
Kafka Broker VM
Processor VM
MongoDB Database VM
```

Synthetic authentication events were generated by the Producer.

The events were published to the Kafka `auth-events` topic.

The events were consumed by the Processor.

Repeated authentication failures were classified.

Processed events were persisted in MongoDB.

Stored security information was retrieved through the REST API.

The following threat-classification progression was demonstrated:

```text
FAILED_LOGIN
FAILED_LOGIN
SUSPICIOUS
SUSPICIOUS
POSSIBLE_BRUTE_FORCE
```

The resulting `POSSIBLE_BRUTE_FORCE` event was persisted in MongoDB and returned through the REST `/alerts` endpoint.

# Assumptions

Several assumptions were made during the implementation.

## Synthetic Authentication Data

The authentication events are synthetic.

The following values were used for demonstration:

```text
username: alice
source_ip: 192.0.2.15
```

These values do not represent a real user or real authentication traffic.

---

## Threat Classification Threshold

The following threshold was used:

```text
1 failure  -> FAILED_LOGIN
2 failures -> FAILED_LOGIN
3 failures -> SUSPICIOUS
4 failures -> SUSPICIOUS
5+ failures -> POSSIBLE_BRUTE_FORCE
```

This is an educational heuristic.

Five failed authentication attempts are not claimed to prove that a real cyberattack has occurred.

---

## Single Kafka Broker

A single Kafka Broker was used.

The Kafka topic uses:

```text
Partitions: 1
Replication Factor: 1
```

Broker-level fault tolerance is therefore not provided.

---

## Single MongoDB Server

MongoDB was deployed as a single database server.

A MongoDB replica set was not configured.

Database-level high availability is therefore not provided.

---

## In-Memory Detection State

The Processor tracks consecutive failed logins using application memory.

The state is maintained using the combination:

```text
(username, source_ip)
```

The counter is reset when the Processor application restarts.

MongoDB retains the processed events, but the current consecutive-failure counter is not reconstructed automatically.

---

## AWS Free Tier

AWS Free Tier resources were available for the project.

Resource availability and cloud cost influenced the architecture.

Additional EC2 instances and managed services were avoided when they were not required.

For example, the REST API was included in the Processor container rather than being deployed on a separate fifth VM.

# Failed Attempts and Resulting Changes

Failures encountered during the assignment were retained as part of the engineering evidence.

---

## Kafka KRaft Initialization

The first Kafka storage formatting attempt failed.

Kafka reported that an explicit controller initialization option was required.

The available options included:

```text
--standalone
--initial-controllers
--no-initial-controllers
```

A single-node Kafka deployment was being used.

The following option was therefore selected:

```text
--standalone
```

Kafka was then initialized successfully.

### Resulting Lesson

The selected Kafka version required explicit KRaft controller bootstrap behavior.

Service-specific version behavior had to be checked rather than assumed.

---

## MongoDB Kernel Compatibility

MongoDB 8.0.29 was installed successfully, but the service initially failed to start.

The failure was investigated using:

```bash
sudo systemctl status mongod
sudo journalctl -u mongod -n 30 --no-pager
```

A compatibility issue with the running Linux kernel was reported.

The Database VM was running:

```text
7.0.0-1012-aws
```

Installed kernels were inspected.

The following compatible kernel was already available:

```text
6.17.0-1017-aws
```

The GRUB configuration was backed up and changed so that the compatible installed kernel would be used.

After reboot:

```bash
uname -r
```

returned:

```text
6.17.0-1017-aws
```

The private Database address remained:

```text
172.31.13.96
```

MongoDB was then started successfully.

A database ping returned:

```text
{ ok: 1 }
```

### Resulting Lesson

Successful package installation did not guarantee that the installed service would run correctly.

Actual service logs had to be inspected.

---

## MongoDB User Configuration

A placeholder password was accidentally used during the first creation of the MongoDB Processor account.

A second attempt to create the account returned that the user already existed.

The existing account was corrected using:

```text
db.updateUser(...)
```

Authentication was then tested independently.

### Resulting Lesson

Placeholder configuration values had to be reviewed carefully before commands were executed.

---

## Processor MongoDB Authentication Failure

The first Processor test successfully consumed Kafka events.

MongoDB insertion failed with:

```text
Authentication failed
```

The `ca0_processor` account was tested directly through Mongosh.

Authentication succeeded.

The following components were therefore known to be working:

```text
MongoDB server
Network path
MongoDB application account
```

The Processor runtime environment configuration was then corrected.

MongoDB insertion succeeded afterward.

### Resulting Lesson

Network, authentication, and application configuration were tested separately instead of changing all layers at the same time.

---

## Kafka Auto-Commit Problem

The first Processor implementation used:

```python
enable_auto_commit=True
```

During the MongoDB authentication failure, Kafka offsets were inspected.

The offsets had advanced even though the database writes had failed.

The implementation was changed to:

```python
enable_auto_commit=False
```

The MongoDB write is now performed first:

```python
collection.insert_one(processed_event)
```

The Kafka offset is committed afterward:

```python
consumer.commit()
```

### Resulting Lesson

Message acknowledgement should occur after successful downstream processing when possible.

---

## Processor Container Lifecycle

The Processor was initially executed using:

```text
docker run --rm
```

during interactive testing.

When the terminal session ended, the Processor container was no longer running.

The final deployment was changed to:

```text
docker run -d
```

with:

```text
--restart unless-stopped
```

### Resulting Lesson

A command appropriate for interactive debugging was not sufficient for a persistent service deployment.

# Verification of AI-Generated Guidance

AI-generated guidance was verified through direct testing.

Several cases required changes after the actual environment behaved differently from the initial recommendation.

---

## MongoDB Verification

A standard MongoDB installation process was initially followed.

The package installation succeeded.

The MongoDB service failed to start.

Instead of assuming that the installation was correct, the following were inspected:

```text
systemctl
journalctl
running kernel
installed kernels
```

A kernel compatibility problem was discovered.

Replacement of the Database VM was considered during troubleshooting.

Because AWS Free Tier resources were being used, unnecessary replacement of the VM was avoided.

A compatible kernel was already installed on the Database VM.

The boot configuration was changed and MongoDB was tested again.

The service then started successfully.

The final solution was therefore selected from observed system behavior rather than accepting the initial installation guidance without verification.

---

## Kafka Offset Verification

The first Processor code used automatic Kafka offset commits.

The implementation worked when MongoDB writes were successful.

During a MongoDB authentication failure, Kafka consumer offsets were inspected.

The offsets were found to have advanced.

This demonstrated that the original implementation did not provide the desired failure behavior.

The implementation was changed to manual commits after successful MongoDB insertion.

The AI-assisted code was therefore modified after failure testing.

---

## Docker Lifecycle Verification

Foreground Docker execution was initially used during testing.

The Processor was later found to be absent from:

```bash
docker ps
```

The final deployment approach was changed to a detached container with a restart policy.

The change was based on observed Docker behavior rather than the fact that the original test command had previously executed successfully.

# AI Critique

AI assistance was useful for explaining unfamiliar technologies and providing starting points for commands and code.

However, generated guidance sometimes depended on assumptions that did not match the deployed environment.

The MongoDB kernel issue demonstrated that a valid-looking installation process could still result in a service that could not start.

The Kafka offset issue demonstrated that code could work during normal operation while still behave incorrectly during downstream failure.

The Docker lifecycle issue demonstrated that a command suitable for testing was not necessarily suitable for final deployment.

For these reasons, AI-generated guidance was treated as a starting point rather than final evidence.


# Open Questions and Limitations

## In-Memory Detection State

Failed-login counters are stored in Processor memory.

The counters are reset when the Processor restarts.

A future implementation could persist the detection state using:

```text
MongoDB
Redis
Kafka state storage
```

---

## Exactly-Once Processing

Exactly-once processing is not provided.

Manual Kafka commits reduce the risk of acknowledging an event before a database write succeeds.

However, a crash after MongoDB insertion but before the Kafka offset commit could result in duplicate processing.

A future implementation could use idempotent writes or a unique `event_id` index.

---

## Kafka Availability

Only one Kafka Broker is deployed.

Broker-level redundancy is not provided.

A production Kafka deployment would normally use multiple Brokers and replicated partitions.

---

## MongoDB Availability

Only one MongoDB server is deployed.

A replica set is not configured.

Database high availability is therefore not provided.

---

## REST Authentication

Application-level authentication is not currently implemented for the REST API.

Broad public exposure should therefore be avoided.

---

## Flask Development Server

The Flask development server is used.

A production deployment would use a production WSGI server.

---

## TLS

End-to-end application-level TLS has not been implemented for every internal service connection.

The assignment deployment relies on private AWS networking and network access controls where applicable.

---

## Threat Detection Logic

The threat-detection rule is intentionally simple.

A production authentication monitoring system could also consider:

```text
time windows
IP reputation
geographic anomalies
authentication rates
device identity
historical account behavior
distributed attack sources
```
